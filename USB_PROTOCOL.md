# PE1 USB protocol — implemented Mac contract

The Mac owns the ramp/step schedules; the board applies the latest channel levels.
Perifit Edge 0.8.0 negotiates two-channel legacy boards and three-channel M3 boards.

## M3 firmware (three-channel form)

The supplied Uno sketch now advertises and requires three channels. HELLO, ARM,
STOP, BOOT, ERR and FAULT retain their existing framing. READY/SET/TEST/ACK are:

```text
PE1 READY <nonce> 3 <maxM1> <maxM2> <maxM3> 1000 TEST250
PE1 SET <nonce> <sequence> <M1> <M2> <M3>
PE1 TEST <nonce> <sequence> <M1> <M2> <M3>
PE1 ACK <nonce> <sequence> ARMED|DISARMED <M1> <M2> <M3>
```

All three advertised maxima must be 1–255. SET accepts zero through each cap;
TEST accepts exactly one nonzero channel and finishes with all three OFF after
250 ms. STOP, invalid input, controller/connection loss and both firmware
watchdogs switch all three OFF. Missing M3 values are rejected, not inferred.
The host verifies ACK arity against the negotiated channel count.

The line limit remains 128 bytes. The current Mac emits two values for old
two-channel boards and three for M3 boards; older Mac versions cannot use M3
firmware. Existing saved records decode missing M3 values as zero. Flash later
with `python3 Firmware/flash_arduino.py`, with external motor power disconnected.

## Legacy two-channel forms and shared requirements

The examples below describe the original two-channel form. Their nonce,
sequence, deadline, framing and shutdown rules also apply to the three-channel
form above; every channel participates in each shared stop.

## Link and numbers

- USB serial, **115200 baud, 8 data bits, no parity, 1 stop bit**, no flow control.
- ASCII lines terminated by LF. CRLF is accepted. Maximum 128 bytes including LF
  and an optional CR; a 128-byte input buffer including the terminating NUL suffices.
- Exactly one space between tokens. No banners, debug prints, or JSON on Serial.
- Sessions are 32 lowercase hexadecimal characters, generated by the Mac.
- Sequence numbers are decimal integers 1…2147483647, strictly increasing within
  a session. Gaps are valid because unsent SET commands may be cancelled by OFF.
- Channels are ordered **M1, M2**. PWM levels are integers 0…255 and must also be
  within each channel's board-advertised limit. Zero means output disabled/released.
- 100% in the app means its discovered maximum, bounded by the board limit. ACK levels are the
  raw PWM values actually written, not percentages or inferred physical vibration.

## Messages

| Direction | Message | Required behavior |
|---|---|---|
| Board → Mac | `PE1 BOOT 1` | Optional boot announcement; outputs are already zero/disarmed. A reset during an active connection causes a host fault. |
| Mac → Board | `PE1 HELLO <session>` | A new session forces both outputs zero, disarms, clears the sequence counter, and permits one ARM or TEST. |
| Board → Mac | `PE1 READY <session> 2 <max1> <max2> 1000 TEST250` | Both channels are zero/disarmed. Limits are 1…255; watchdog is exactly 1000 ms. |
| Mac → Board | `PE1 ARM <session> <seq>` | Accept only a fresh HELLO session, with both outputs zero. Enter armed state; start watchdog. |
| Mac → Board | `PE1 SET <session> <seq> <pwm1> <pwm2>` | Accept only while armed. Validate the complete pair, apply both, refresh watchdog, then ACK. |
| Mac → Board | `PE1 STOP <session> <seq>` | Set both outputs zero and disarm. End permission to SET or ARM in this session. |
| Board → Mac | `PE1 ACK <session> <seq> <ARMED\|DISARMED> <pwm1> <pwm2>` | Acknowledge every accepted ARM/SET/STOP after applying it. ARM reports `ARMED 0 0`; STOP reports `DISARMED 0 0`. |
| Board → Mac | `PE1 ERR <session> <seq> <CODE>` | Invalid command: outputs must already be zero/disarmed. Use sequence 0 if it could not be parsed. |
| Board → Mac | `PE1 FAULT <session> <CODE>` | Asynchronous fault, including `WATCHDOG`: outputs must already be zero/disarmed. |

`CODE` is a short uppercase token with underscores, e.g. `BAD_FRAME`,
`BAD_SESSION`, `BAD_SEQUENCE`, `OUT_OF_RANGE`, `NOT_ARMED`, `OVERFLOW`,
`NEW_SESSION_REQUIRED`, or `WATCHDOG`. Before any HELLO, use 32 zeroes as the
session field in errors. Never echo unbounded or unvalidated input.

A repeated HELLO with the same nonce is idempotent only before that session's
first ARM or TEST. Return READY again without changing state. After ARM, TEST, STOP, or a fault,
another ARM or TEST requires a **different** HELLO nonce. A duplicate/stale command must
never restore nonzero output. Invalid commands force zero/disarm and do not renew
the watchdog. After an overlong/invalid line, discard through the next LF so a
suffix cannot be interpreted as a new command.

## Timing and stopping

- The Mac computes independent envelopes at 50 Hz. Ramp uses the original
  Edge-o-Matic increment: `(target - start) / rampSeconds / 50`.
- Normal SET updates/heartbeats carry the latest pair at 10 Hz. No queue of future
  steps is sent. Stepped-ramp intervals are 100 ms or longer.
- A channel being set to zero, a shared risk cutoff, and STOP bypass normal
  throttling. The host removes wholly unsent SET frames; a partly transmitted
  frame is finished before the urgent command, preserving framing.
- A zero SET during cooldown keeps the board armed and renews its watchdog.
  Resume starts each envelope at its configured starting level.
- STOP disarms. Reconnection or a delayed SET cannot resume output. The next
  manual app Start performs a fresh HELLO, then ARM.
- The Mac faults on a missing or inconsistent ACK after 900 ms, a stalled
  controller after 700 ms, disconnect, malformed data, or unexpected reset. It
  attempts STOP and closes the port; it never automatically rearms. The app may reconnect the same port with a fresh
  HELLO to confirm OFF; a new manual Start is still required for ARM.
- The board must independently set both outputs to zero and disarm after **1000
  ms without a valid fresh ARM/SET**. Repeated sequence numbers, invalid traffic,
  HELLO retry noise, and arbitrary Serial activity must not extend this deadline.
- Use unsigned elapsed-time subtraction so the board's `millis()` wrap is safe.
  Add and test an AVR hardware watchdog for firmware hangs; do not rely solely
  on a loop-based timeout.
- The host allows five seconds for boot/handshake and retries HELLO every 500 ms.
  Once READY is sent, all command handlers and ACKs must be nonblocking and fast.

## Watchdog execution and bounded shutdown

- The Mac serial worker runs on its own serial queue, independent of the UI
  actor. Controller updates carry their production timestamp and generation;
  heartbeat transmission and ACK reception cannot refresh the 700 ms lease.
  ARM ACK starts a zero-output lease; fresh drive updates are required afterward.
- Host ACK deadlines are absolute from enqueue, including partial transmission.
  Up to 64 pending commands are bounded in memory, with one slot reserved for
  STOP. Wholly unsent normal SET frames coalesce to the latest pair without
  extending their original deadline; urgent zero transitions remain ordered.
- On Stop/fault, revoke the generation and cancel unsent output commands. Finish
  only a frame already partially written, then STOP. Retry nonblocking writes
  for at most 100 ms; the entire STOP acknowledgement budget remains 900 ms.
  A failed shutdown closes USB and leaves reported output unknown. The board's
  independent 1000 ms deadman remains the fallback.
- The AVR hardware watchdog is fed only after servicing protocol deadlines and
  observing the millis clock advance. A frozen Timer0 timebase therefore causes
  a hardware reset even if the main loop continues running.
- A pending board response with no TX progress for 100 ms forces immediate
  zero/disarm, cancels TEST, and consumes the session. `PE1 FAULT <session>
  TX_STALL` is sent after any already-partial response can finish. It uses the
  existing FAULT frame; no new wire version or verb is introduced.
- Reconnect can confirm zero/disarmed output only. Sleep, Stop, disconnect and
  replacement connections invalidate previous controller generations. No
  watchdog fault or reconnection automatically resumes motors.

## Pattern playback (app v0.6)

Wave and pulse patterns require no additional wire messages or firmware state.
The host samples each channel's independent waveform using elapsed time and sends
ordinary SET pairs at the existing rate. The board applies the latest bounded
pair; it must not queue a pattern or run one autonomously after host commands end.
Zero-valued pattern sections disable that channel. All shared cutoffs send zero
for both channels; STOP and the independent firmware watchdog still disarm.
Pattern shape/configuration is saved by the Mac, not transmitted as executable
scripts. The 10 Hz link is intended for these slow motor patterns, not audio or
sample-accurate e-stim waveform playback.

## Discovery extension: TEST250 (app v0.4)

New firmware MUST advertise `PE1 READY <session> 2 <max1> <max2> 1000 TEST250`.
The host parses original seven-token READY for diagnostic connection, but blocks
discovery and normal app sessions without TEST250. Other PE1 rules still apply.

- Command: `PE1 TEST <session> <seq> <pwm1> <pwm2>`.
- Accept only in a fresh unused HELLO session, with both outputs OFF. Validate
  both levels before applying either: exactly one nonzero, within board limits.
- Consume ARM/TEST permission immediately. Apply that one motor level with a
  **250 ms board-local deadline**. Keep the other motor disabled. This is TEST
  state, not normal ARMED operation. No immediate ACK; SET, ARM or another TEST
  must not extend or replace the pulse (invalid traffic zeros/disarms).
- Independently of host traffic, disable both outputs at the deadline and send
  exactly one `PE1 ACK <session> <seq> DISARMED 0 0`. The host's 900 ms
  ACK timeout includes the pulse. No blocking delay: STOP, parser faults,
  reset handling and watchdog must still run.
- STOP, new HELLO or fault cancels both the pulse and its pending completion ACK
  immediately. Send the STOP ACK/new READY/fault response instead. The host
  tolerates an already-in-transit TEST ACK after it requests STOP.
- TEST cannot renew the ordinary 1000 ms ARM/SET deadman. Use wrap-safe elapsed
  timing and retain the AVR hardware watchdog for a firmware hang.
- Completion/cancellation consumes the session. Another TEST or ARM requires a
  **different** HELLO nonce. Mac tests are manual, one at a time, require feedback,
  and wait two seconds after completion before another pulse.
- Board caps are electrical bounds chosen outside this protocol. TEST250 does
  not imply sensing/identification. ACKs do not measure motor behavior or current.

Example after electrical compatibility is verified:

```text
Mac:   PE1 HELLO aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
Board: PE1 READY aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa 2 200 180 1000 TEST250
Mac:   PE1 TEST aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa 1 8 0
       [M1 only, 250 ms; board then disables both outputs]
Board: PE1 ACK aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa 1 DISARMED 0 0
```

Test missing host/unplug, STOP during pulse, malformed traffic, two nonzero
levels, repeats, invalid levels, clock wrap and absent TEST250. A host hang must
not stretch the test to the ordinary one-second deadman.

## Golden exchange

```text
Mac:   PE1 HELLO 0123456789abcdef0123456789abcdef
Board: PE1 READY 0123456789abcdef0123456789abcdef 2 200 180 1000 TEST250
Mac:   PE1 ARM 0123456789abcdef0123456789abcdef 1
Board: PE1 ACK 0123456789abcdef0123456789abcdef 1 ARMED 0 0
Mac:   PE1 SET 0123456789abcdef0123456789abcdef 2 120 72
Board: PE1 ACK 0123456789abcdef0123456789abcdef 2 ARMED 120 72
Mac:   PE1 SET 0123456789abcdef0123456789abcdef 3 0 0
Board: PE1 ACK 0123456789abcdef0123456789abcdef 3 ARMED 0 0
Mac:   PE1 SET 0123456789abcdef0123456789abcdef 4 80 36
Board: PE1 ACK 0123456789abcdef0123456789abcdef 4 ARMED 80 36
Mac:   PE1 STOP 0123456789abcdef0123456789abcdef 5
Board: PE1 ACK 0123456789abcdef0123456789abcdef 5 DISARMED 0 0
```

The example limits 200/180 are test values, not motor-rating recommendations.
Advertise limits chosen for the verified motors, supply, and simultaneous load.
A later SET using this ended session must fail and leave both motors OFF.

The emulator validates host behavior, not real electrical fail-off, motor current,
mechanical vibration, or the installed firmware. Verify those on the actual board.
